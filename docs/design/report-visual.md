# Design — report module (adhoc, plan and audit)

> Status: validated in owner brainstorming (2026-08-04, revised the same
> day). Direct input to the later report phase. Requires two new ADRs
> **before coding**.
> Parent principle: the LLM produces structured CONTENT; a deterministic
> machine assembles the report. An LLM never writes report HTML/CSS/JS.

ADR-010 later cut v1 to the versioned JSON contract, the audit walker, the
deterministic Markdown projection, `jacu_report` and `jacu statusline`, with
no HTTP, browser, UI, `go:embed`, HTML, JavaScript or frontend dependency in
that phase. That cut **defers** this factory; it does not revoke it. Each
visual/HTTP piece still needs its own ADR and gates. No consumer may treat
Markdown as the source of state.

## Problem

Long LLM prose does not scale for an autonomy model, and audit must be
evidence generated from real state, not a model's self-report. Every relevant
output (asked report, plan, audit) needs rich, standardized HTML owned by the
project.

## Three modes, one contract, one factory

| Mode | Content source | Interaction | Use |
|---|---|---|---|
| `adhoc` | LLM (analysis, research, comparison, system design) | None — request, validate, render, save | Everyday “make a report of X” with no interview |
| `plan` | LLM plus user choices | Clickable decision points → JSON → LLM reads → clarity gate | Planning interview |
| `audit` | **Runtime** (missions, verdicts, receipts) | Read-only | Evidence that supports the final OK |

`plan` is an adhoc that talks; `audit` is an adhoc nobody writes. The report
system is the product; planning is one use of it.

## Architecture

```
LLM ──(JSON content, never code)──► jacu
                                      │ validate against versioned schema
                                      │ organize files
                                      ▼
                           report factory (stateless)
                           embedded in the Go binary (web/ + go:embed)
                           JSON in → self-contained HTML out
                                      │
                 ┌────────────────────┴──────────────────┐
                 ▼                                        ▼
     render mode (headless)                    serve mode (planning)
     static HTML, CI-friendly                  127.0.0.1 ephemeral;
                                               user clicks write back
                                               into project JSON; dies
                                               at session end
```

- **Pure factory:** stores nothing. No database, no factory-owned state.
  User decisions persist in the project's `*.report.json` (owner: JACU),
  never in the app.
- **Core independent of viewer:** headless (CI, executor) validates schema
  and exports static HTML from the same embed. Browser is optional, never a
  dependency.
- **MCP stays STDIO-only.** The local server is a mode, not a daemon.

## Contract (`*.report.json`)

- Versioned JSON schema (`schema_version`), owner: JACU. Field `kind:
  adhoc | plan | audit`.
- **Authorship format — JSON envelope, Markdown prose:** structure is JSON
  validatable by schema; text fields may hold Markdown converted
  deterministically by the factory. Pure Markdown was rejected because it
  does not validate against schema without a convention-parser.
- **v1 blocks (8):** `summary`, `steps`, `decision`, `risks`, `flow`,
  `chart`, `table`, `metrics`. More only with proven use, versioned by
  `schema_version`.
- **Block `flow` = graph as DATA** (nodes, edges, groups/lanes; optional
  `tech` tag such as `postgres`, `aws-lambda`, `react`). The LLM never
  writes diagram syntax; it describes structure.
- **The LLM chooses BLOCK, never library.** Deterministic factory mapping in
  HTML: `flow` → @xyflow/react + elkjs layout + motion animation + icons via
  a registry (Iconify: Simple Icons, Devicons, Carbon, MDI plus official
  AWS/Azure/GCP sets — licences checked at design time; unknown tech ⇒
  generic icon, never a break) · `chart`/`metrics` → embedded chart library ·
  `table` → sortable. Mermaid is NOT rendered in HTML and is not authored: it
  is an OUTPUT of the `.md` projection (the factory converts the `flow`
  graph to textual mermaid — the format an LLM reads as a graph).
- **Typed decision points** (`kind: plan` only):
  `{id, question, kind: options|multi|text, options[], answer}`. No x/y
  positions; layout by preset.
- `audit` is **generated by the runtime** from missions, verify verdicts,
  receipts and diffs. Read-only. No click edits evidence.

## Planning loop (the later-phase “interview”)

```
LLM proposes plan.report.json with open decision points
→ jacu validates → serve opens in the local browser
→ user clicks choices → recorded in the JSON
→ LLM reads the JSON (never the HTML) → refines → repeats
→ open_decisions == 0  ⇒  “questions exhausted” lint passes
→ compile mission/program
```

“Exhaust questions before start” is mechanical: `open_decisions == 0`.

## Clarity gate

After `open_decisions == 0`, before execution:

```
host opens a session with the cheapest model, clean context
→ receives only the plan PROSE (structured fields hidden/redacted)
→ returns structured readback: what changes, paths, verify commands,
  acceptance criteria
→ jacu compares readback × real mission fields — pure deterministic
  computation; JACU does NOT call an LLM (model-router stays deferred)
→ score ≥ floor: release execution and report the suggested executor tier
→ score < floor: divergences become new decision points and return to the
  visual interview
```

A good spec is one the cheapest model understands (clarity canary).
“Did you understand?” is never a question — the probe is falsifiable by
comparison with mission fields. Understanding ≠ capability: the probe is a
clarity floor, not a substitute for executor-tier choice by
risk/complexity. The comprehension score appears on the plan's visual
report.

## File layout in the target project

```
<project>/
├── .jacu/reports/           # *.report.json — source of truth, runtime-owned
└── docs/jacu/               # git-versionable projections
    ├── reports/YYYY-MM-DD-<slug>.html
    ├── reports/YYYY-MM-DD-<slug>.md
    ├── plans/…​.html + …​.md
    ├── audits/…​.html + …​.md
    └── index.html           # generated; lists and links everything
```

### Two projections, one source (read rule by consumer)

The factory emits from the SAME JSON, deterministically:

- **HTML** — human. Rich: animated flows with technology icons (xyflow +
  elkjs + motion + Iconify), interactive in plan mode. Full system-design
  visual standard even when the report is not architecture.
- **`.md` digest** — LLM. Compact: drops presentation (presets, layout,
  animation) and keeps content; `flow` blocks become textual mermaid (LLMs
  read graphs natively); `table`/`metrics` become Markdown tables.

Hard consumption rule: **an LLM never reads HTML** (nor a screenshot).
Content context = `.md` digest (cheaper). Plan-mode loop (decision-point
answers) = structured `.report.json` fields. Human = HTML. Implementation
cost is near zero: the same block walker that emits HTML emits Markdown.

A committed audit is permanent project history — it supports the final-OK
model on `main`.

## MCP surface

**At most one new tool** (`jacu_report`: validate content / read decisions).
Render, export, open and layout are runtime or CLI (`jacu report ...`),
never an LLM decision. Render/open/export/list as tools would blow the
first-order ceiling and are not model choices.

## ADRs required before coding

1. **Local HTTP:** exception to STDIO-only. Strict scope: bind 127.0.0.1,
   viewer/decision routes only, lifetime = planning session. The proven need
   is interactivity (static HTML does not persist a choice).
2. **Embedded frontend:** exception to “no new dependency”. `web/` in the
   repo (Vite + React + @xyflow/react + elkjs + Tailwind), build ONLY in CI
   (`npm ci` strict, pinned lockfile, audit in the CI-hardening workflow),
   `dist/` never committed, `go:embed` at release. Rejected alternative
   (download a public repo at runtime): violates the threat model —
   download-and-execute is exactly what JACU forbids.

## Skill rules (`jacu-report`, born with the module)

1. Generate only schema-valid JSON; validate before return.
2. Never generate HTML/CSS/JS/React.
3. Short text; visual first.
4. No x/y positions; layout presets.
5. Long detail stays collapsed.
6. Read decisions from JSON, never from HTML.

## Budgets and gates

- Cold start p95 < 150ms and idle RSS < 40MB still apply WITH the embed —
  measure before freezing; if exceeded, the embed leaves the critical path
  (lazy).
- Golden tests: same JSON ⇒ same byte-identical HTML (deterministic render).
- Fuzz the report parser (same pattern as other phases).

## Roadmap fit

- The module is part of the later report/plan-interview design: the visual
  interview is program compile; the audit report is the audit package.
- Suggested internal order: contract + validation + headless render →
  interactive serve mode → rich canvas viewer (iterative, after).
- Official cloud icons, extra blocks, SQLite: out of v1, with their own
  trigger. YAGNI.

## Out of scope (explicit)

Any factory-owned state · report editable after execution · MCP tools for
render/export/open/list · LLM writing presentation markup or diagram syntax ·
Mermaid rendered in HTML (it is only a digest projection).
